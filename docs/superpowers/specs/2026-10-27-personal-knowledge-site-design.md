# 个人知识站（暂名 life）设计文档

## 1. 初衷（为什么做）

用户的核心问题：学习素材没人整理、放得杂乱。典型例子：在 B 站看到好的前端动效，收藏/订阅后懒得再看；改为截图发微信，但图片无法搜索，日后找不回来，也无法维护。

结论：问题出在"收进来的那一刻"。收藏只是换个地方堆放；截图快但不可搜。用户要的是：**收得和发微信一样快，但收进去的东西事后能搜、能用。**

目标是维护一个**唯一的信息来源**，顺手、美观，让用户有动力往里放东西。最终每条内容应当是一份"完整的使用说明/介绍"（知识类），而不是一张截图或一个链接。

## 2. 目标

- 手机（外出时）和电脑都能随时往里丢：链接、图片、文字。
- 丢进去的原料由整理助手（DeepSeek）整理成完整条目。
- 信息不足时，助手自己上网查补充，并向用户提少量简单问题。
- 原料永不丢失：投递即保存，整理失败也不影响。
- **顺手是最高原则**，高于美观。

## 3. 非目标 / 反目标

- 非目标：公开访问、SEO、评论、访客统计。站点仅用户自己使用。
- 非目标（第一版）：搜索、旅行日志、随笔、小工具页。
- 反目标（即便技术上能用也算失败）：
  - 投递时要求用户选分类、填标签、填表单。
  - 助手未经确认直接改写/覆盖用户的原文。
  - 内容锁在某个软件里，无法导出。
  - 用户为了维护而需要自己改代码。

## 4. 用户已决定的

- 仅自己使用，需登录保护；手机在外面也要能访问和投递。
- 用户懂代码但不想自己改；日后改功能由 Claude 完成。
- 整理助手使用 DeepSeek（"deepseek harness"）：补全用户没说明的信息、需要的信息、格式。
- 信息不足时：助手**上网查补充 + 向用户提问**（不是标记后搁置）。
- 外观参考 Claude 的风格（暖色纸张底色、安静、文字优先）。外观用户会边用边调，不必一次到位。
- 第一版只做一件事：**随手丢东西 → 助手整理**。

## 5. 第一版范围（v1）

### 5.1 投递
- 一个输入框，放在首页最显眼位置，手机/电脑一致。
- 支持：粘贴链接、粘贴/选择图片、输入文字，可混合。
- 点发送即**立刻保存原料**，不等待助手。不要求选分类。

### 5.2 整理（后台）
- 助手读取原料：文字、链接页面内容、图片中的文字（OCR/视觉识别）。
- 信息不足时（如仅有视频链接、看不到内容）：自行联网查补充；仍有缺口则向用户提少量简单问题。
- 产出一份**草稿条目**，用户确认后入库；未确认前不覆盖任何内容。

### 5.3 条目结构
标题、一段说明、关键信息/步骤/要点、原链接、原图（保留）、自动生成的标签；图片中识别出的文字存为可检索文本。条目的具体字段/模板按内容类型（如前端动效）由助手生成，细节留给实现者。

### 5.4 待确认队列
用户可看到"待确认草稿"和"助手的提问"，一键确认或回答。

## 6. 默认方案（Claude 的选择，非用户所选）

- 托管在云上（如 Vercel 一类），有独立网址；手机可"添加到主屏幕"（PWA）。
- 数据存为纯文本文件（Markdown + 图片文件），随时可导出；具体存放位置（Git 仓库/对象存储/数据库）由实现者定。
- 登录方式由实现者定（单用户，越省事越好）。
- DeepSeek 通过其 API 调用；联网查补充的实现方式由实现者定。

## 6.1 评审后补充的决定（Claude 的选择，待用户过目）

- **数据**：私有 Git 仓库里的 Markdown + 图片文件是唯一真源；用户可用任何编辑器直接改，"导出"即克隆仓库。后台任务通过提交到仓库写入。
- **后台整理**：异步队列，可接受数分钟；v1 不做推送通知，用户下次打开看"待确认队列"即可。
- **确认**：可 原样接受 / 编辑后接受 / 丢弃 / 附一句话让助手重做。助手有疑问时，同时产出尽力而为的草稿和问题，草稿不被问题阻塞。已入库条目可再编辑。
- **原料与条目**：原料进"收件箱"，与条目分开存放；v1 一条原料对应一个条目，合并多条留待后续。条目保留原始文字原文。
- **语言**：界面和条目输出一律中文；英文来源由助手翻译/概括，保留原文链接。
- **登录**：单用户，长期有效的口令会话。
- 假设用户没有现成的域名/托管账号/仓库，由实现者提议默认值。

## 6.2 用户对评审问题的回答

- **手机是 iPhone。** 投递入口需包含 iOS 的"分享"通道（如 iOS 快捷指令，经分享菜单把链接/图片/文字 POST 到站点接口）；PWA 作为打开网站的补充。这是"顺手"目标的关键，v1 必做。
- **视频链接场景**：助手只用标题、简介和联网查到的资料即可，用户会自己补一句简单描述。无需抓字幕或抽帧。
- **联网搜索**：用户自有项目 https://github.com/sweetcornna/free-search-mcp（Python 3.11+、无需 API key、本地运行的 MCP 服务，提供 search / research / fetch / read_doc 等工具）作为助手的搜索与网页抓取后端。它是常驻 Python 进程，不适合无服务器托管，因此需要一台能常驻运行的小服务器（见 §6.3）。
- **图片识别（Claude 的选择）**：DeepSeek 不看图，默认在服务端用本地 OCR 提取图中文字，不把截图发给第三方；纯画面内容靠用户补充的描述。

## 6.3 服务器与 DSH 接入（用户已决定租一台常驻服务器）

- 服务器上跑：站点、整理任务队列、free-search-mcp、DSH。托管不再用无服务器方案（取代 §6 的 Vercel 默认）。
- **DSH 接入方式已验证，用户已有可用实现**（本地 demo，见用户的 `dsh-embed` 项目，其说明如下，实现者以此为准）：
  - 常驻子进程 `dsh --profile sdk-minimal`，通过 stdio、换行分帧的 JSON-RPC 2.0 通信。
  - 必须先 `initialize`（参数 provider=`deepseek-official`、model=`deepseek-v4-pro`、cwd）成功，之后 `session/prompt`（contentBlocks）才被接受；返回的 messageId 仅表示已入队。
  - 回复通过 `session.event` 通知流式返回：`turn/start`、`assistant/message`（按 message.id 分组；文本取 `type=text` 块，`reasoning` 块单独处理）、`turn/end`；`session.status` 给出 running/idle。
  - 需要把 `DSH_HOME` 指向项目内独立目录；spawn 前剔除继承来的 `DSH_PROFILE`、`DSH_WEB_URL` 等环境变量。API key 从 `~/.dsh/.credentials.yaml` 读取，只注入子进程环境。
  - 该 demo 只监听 127.0.0.1、无鉴权、会话为进程内单例。
- **安全要求（硬性）**：`sdk-minimal` 的沙箱策略是 danger-full-access，且助手会读取不可信的网页内容（有提示注入风险）。部署到公网服务器时，必须收紧：专用低权限系统用户或容器、限制 agent 工作目录、profile 中收紧 sandbox-policy，站点接口必须鉴权。
- **Linux 服务器上的 dsh（Claude 已调查，实现时需在服务器上实测）**：Mac 上的 `dsh` 只是借桌面 App 自带 Electron 启动的脚本，但同一套 CLI 以 npm 包发布：`@deepseek-ai/dsh`（公共 npm，当前 0.2.1-rc.2，提供 `dsh` 命令）；profile 由 `@deepseek-ai/dsh-base`、`dsh-sdk-minimal` 等包组成，且含 Linux 沙箱组件（landlock）。预期安装：服务器装 Node 24，`npm i -g @deepseek-ai/dsh`，再在服务器上配置 DeepSeek API key（`~/.dsh/.credentials.yaml` 或环境变量，不得进仓库）。这是预发布版本，版本需锁定；若某步装不上，实现者回来找用户。
